# Karaoke Studio — комплексный аудит и план исправлений

Дата: 2026-08-31. Объём: 763 файла (front — 515, backend — 171, scripts — 60, cloudflare — 10).

## Методология и охват

Семь параллельных агентов провели построчное чтение кодовой базы по зонам (крупные/сложные/критичные файлы — целиком; во фронтенде и мелких build-скриптах часть файлов вне приоритета просмотрена структурно, не построчно — см. раздел 5). Зоны:

1. **Backend AI pipeline** (`backend/AI/`, 35 файлов).
2. **Backend app/API/БД/очереди** (`backend/app/`, `backend/*.py`, ~48 файлов).
3. **Нативная аудиоподсистема** (`backend/engines/wasapi`, `backend/engines/asio`, `app/services/monitor_*`, `audio_service.py`, `recording_service.py`).
4. **Electron-оболочка + RGB-подсветка** (`front/electron/`).
5. **Frontend React** (`front/src/`).
6. **Online Room + Cloudflare** (`cloudflare/`, room-компоненты фронтенда).
7. **Сборка/релиз/зависимости/тестовая инфраструктура** (`scripts/`, `.bat`, package.json/requirements, тесты).

Это **статический анализ кода**. Раздел 5 честно фиксирует, что не проверялось (требует запуска приложения).

## Часть 3 — Детальные находки по подсистемам (по всем линзам)

### 3.1 Backend AI pipeline (`backend/AI/`)

**Архитектура/AI pipeline:** `KaraokePipeline` оркестрирует: decode → separate (MSST, отдельный процесс) → vocal cleanup (ffmpeg) → pitch (FCPE) + music (librosa, параллельно) → transcribe (пользовательский текст → LRCLIB/pisni.org.ua → ASR) → align (Qwen3/CTC, многоуровневый repair) → voice anchoring (VAD) → notes → validate + atomic publish. Многократные GPU↔CPU "парковки" моделей между стадиями ради экономии VRAM — намеренный, но дорогой трейдофф (несколько операций переноса по сотни МБ–2 ГБ на прогон).

**Управление AI-моделями:** sha256 проверяется только для 1 из 5 моделей (High, см. 2.3.16). `install_models.py` не имеет функции выгрузки/удаления моделей с диска. Параллельная установка нескольких моделей через `ThreadPoolExecutor` создаёт десятки одновременных HTTP-соединений к одному CDN — известный частично закрытый риск (комментарий про `HF_HUB_DISABLE_XET=1`).

**Качество AI-результатов:** ноты без "владельца"-слова отбрасываются целиком (Medium, см. 2.4). Оценка "hop" между кадрами берётся медианой по глобальному списку, не по каждому сегменту — неточность длительности нот на границах. `_syllable_weight` (word_voicing.py) считает "слоги" по гласным буквам, смешивая кириллицу и латиницу — для RU/EN-смешанных текстов даёт неверные веса alignment. При полном отсутствии валидного кандидата слово получает вырожденный интервал (`start==end`) без единого лога/предупреждения — тихая деградация без диагностического следа.

**Детерминизм:** нет управления seed/детерминированным режимом inference; fp16 на CUDA для ASR/aligner не гарантированно детерминирован. `discover_lyrics()` зависит от состояния сети в момент запроса — повторная обработка в другой день может пойти по другому источнику текста, каскадно меняя весь alignment. `processing_modes.py` подбирает `batch_size` по текущей свободной VRAM/RAM — зависит от нагрузки машины в моменте.

**Кэширование:** `cache.py` — полная заглушка (High, см. 2.3.14). `install_models.py._hash_cache` кэширует sha256 по `(size, mtime_ns)` — на файловых системах с грубой гранулярностью mtime теоретически уязвим к подмене файла с тем же размером в окне разрешения. `runtime.py._plan` — модуль-глобальный кэш плана без TTL, переоценивается только с `force=True` (в реальности всегда передаётся из `app/`, но не защищено инвариантом).

**GPU/CPU fallback:** Blocker п.2.1.1. Фолбэк на CPU при сбое CUDA реализован только для separation, и то по хрупкому текстовому маркеру ошибки (High, см. 2.3.18). Нет обработки случая "GPU есть, но VRAM не хватает даже одной модели" — прямой `CUDA out of memory` без фолбэка.

**DSP/audio quality:** статический (по всему треку) порог гейта шумоподавления в `vocal_preprocess.py` — риск "съедать" тихий вокал в куплетах или пропускать эхо в тихих участках. Нет финального лимитера/проверки клиппинга после DSP-цепочки ffmpeg.

**Совместимость форматов:** декодирование полностью делегировано ffmpeg (сильная сторона). `separation.py:191` — жёсткий отказ вместо ресемплинга при несовпадении sample rate MSST-выхода. Нет явных проверок на "нулевую длительность"/видео без звука на самом раннем этапе.

**Целостность песенного проекта:** `publish_files_atomically` не восстанавливается после краха между двумя `os.replace` (High, см. 2.3.17). `validate_lyrics_document` — качественная валидация (защита от NaN/Infinity, версия схемы), но проверка перекрытия нот пропускается для `source=="kar"`.

**Стабильность/отказоустойчивость:** ни один `run_ffmpeg` не имеет таймаута (High, см. 2.3.15). Таймаут инициализации MSST-воркера жёстко зашит в 300с без конфигурации. Watchdog-поток `stop_with_parent` зависит от `psutil` в try/except — при недоступности `psutil` осиротевший MSST-процесс может работать неограниченно долго при аварийном убийстве родителя (Medium-High). `ProcessingCancelledError` не проверяется внутри самих долгих forward-проходов ASR/aligner — отмена срабатывает только между этапами.

**Lifecycle:** эскалация остановки процесса (`separation.py.close()`) реализована аккуратно (мягкий сигнал → join → terminate → join → kill). `_release_engines`/`_park_engines` не оборачивают каждый `close()` в свой try/except — сбой одного движка прерывает освобождение остальных именно когда это важнее всего.

**Race conditions:** `AICoreService._lock` (семафор) и модульный `_lock` синглтона — совпадение имён, располагает к путанице при рефакторинге (Low). Семафор нереентерабелен — сейчас безопасно, но не защищено assert'ом.

**Память/ресурсы:** `release_torch_memory()` вызывается в ключевых точках. Основной риск утечки — осиротевший MSST-процесс без `psutil` (см. выше).

**Многопоточность/async:** полностью синхронный модуль (без asyncio), параллелизм через `ThreadPoolExecutor`/`multiprocessing` — классических asyncio-deadlock паттернов не найдено.

**Error propagation:** best-effort телеметрия осознанно проглатывает все исключения (`except Exception: pass`, задокументировано). `utils/io.py.read_json` молча возвращает `default` при `(OSError, ValueError)` — "файла нет" неотличимо от "файл битый". Несогласованность стиля: где-то подробное логирование каждого repair-шага, где-то — полностью тихий fallback.

**Качество кода / дублирование / мёртвый код / сложность / naming / техдолг:** см. отдельный сводный раздел «Аудит качества кода» ниже — материал по AI-пайплайну там расписан полностью.

**Public interfaces:** `AI/__init__.py` объявляет узкий `__all__`, но `app/` напрямую импортирует `AI.cache`, `AI.model_registry`, `AI.install_models`, `AI.lyrics_document`, `AI.pitch_post`, `AI.notes`, `AI.runtime`, `AI.utils.*`, `AI.models`, `AI.version`, `AI.audio` — модуль не инкапсулирован (Medium-High).

**Тестирование:** коммит `8b36849 "refactoring"` удалил и консолидировал часть прицельных AI-тестов. Не найдено тестов на: реальную работу `compute_mode="cpu"` для pitch/ASR/aligner/CTC (только на выставление env-переменной), windowed alignment для длинных песен, восстановление после осиротевшего `.bak`.

### 3.2 Backend app/API/БД/очереди (`backend/app/`)

**Архитектура:** `pipeline_service.py` перегружен (см. качество кода). Циклическая зависимость через lazy-import между `pipeline_service.py` и `app_settings_service.py`.

**Стабильность:** `_normalize_writable_directory` синхронно пишет пробный файл на потенциально сетевой диск без отдельного таймаута — недоступный сетевой путь может подвесить весь HTTP-запрос `/settings PATCH` на ОС-таймаут. `remote_log_service.py`/`metadata_enrichment_service.py` — таймауты и backoff сделаны аккуратно, не блокируют основной пайплайн. `_acquire_processing_slot` не имеет верхнего таймаута ожидания слота — зависший AI-подпроцесс во главе очереди блокирует все остальные песни бесконечно (Medium, см. 2.4).

**Отказоустойчивость:** падение AI-подпроцесса/OOM — перехватывается общим except, статус переводится в ERROR корректно. Нет предварительной проверки свободного места на диске перед стартом длительной операции — узнаём о нехватке только через `ENOSPC` посреди работы.

**Восстановление состояния:** `_mark_interrupted_jobs` не включает `CANCELLING` (Critical, см. 2.2.3). Импорт song-пакета (room import) восстанавливается образцово через журнал транзакций с фазами `prepared/backup-created/published/db-committed`. `cache_service.recover_optimization_transactions/state()` — пустые заглушки (см. качество кода).

**Lifecycle:** single-instance lock реализован через file-lock + HTTP health-check + отложенный импорт приложения — продумано хорошо. daemon-потоки без join при shutdown; `lifespan()` finally не вызывает `pipeline_service.cancel_all_active_processing()` при обычном graceful shutdown (Medium, см. 2.4). `metadata_enrichment_service.enqueue()` — до 8 параллельных daemon-потоков без общего лимита, конкурируют за CPU с реальной обработкой песен.

**Race conditions:** гонка двойного `/process`/`/reprocess` (High, см. 2.3.11). `import_package` не проверяет `is_processing` (Medium, см. 2.4). `delete_song` без локов (High, см. 2.3.12). `enrich_song` пишет в `output_dir` без локов (тот же класс проблемы). `song_content_lock` держится на всю длительность reprocess (Medium, см. 2.4).

**Память/ресурсы:** сессии SQLAlchemy закрываются систематически, утечек не найдено. Файловые хендлы (`_ProgressCapture`) закрываются в finally. `revision_cache._cache` растёт без верхней границы (низкий риск при типичном масштабе библиотеки). `remote_log_service._PENDING_EVENTS` ограничен корректно.

**Многопоточность/SQLite:** WAL-режим + `busy_timeout=30000` + `pool_pre_ping=True` — правильная конфигурация. Порядок захвата блокировок (`_settings_lock → library_write_lock`) не задокументирован явно как инвариант — риск для будущего рефакторинга.

**Файловая система:** `atomic_write`/`atomic_write_bytes` реализованы качественно (fsync + `Path.replace` + fsync директории). Длина имени папки песни обрезается до 180 символов, но не учитывает длину абсолютного пути пользовательской `songs_folder` — риск превышения `MAX_PATH=260` на некоторых системах.

**Целостность песенного проекта:** очень тщательная валидация импорта пакета (zip-бомбы, символические ссылки, реальная декодируемость WAV/FLAC через ffprobe). Экспорт проверяет декодируемость аудио перед `DONE`.

**Состояния Song:** таблица переходов не enforce'ится строго (`_update_progress` только warning). Тупик `CANCELLING` (Critical). Что если процесс убит между `PROCESSING` и `DONE`? — commit атомарен, но при убийстве до commit ретрай не переиспользует уже готовые артефакты (не баг корректности, но потеря готовой работы).

**Данные:** ручные `ALTER TABLE`-миграции без версионирования схемы; `_repair_corrupted_audio_settings` — прямое свидетельство прошлых поломок схемы в проде (Medium).

**API-контракты:** `tempo_override` — рассинхрон типов (ORM `Float` vs Pydantic `int`) — работает только пока инвариант не нарушен. `PATCH /preferences/{namespace}` принимает `dict[str, Any]` практически без валидации структуры.

**Кэширование:** `cache_service.cache_size()` — TTL-кэш без блокировки при конкурентном доступе (не гонка данных под GIL, но дублирование дорогой работы). `revision_cache` — безопасность обеспечивается вызывающим кодом (локами), не самим кэшем — риск при будущем новом вызывающем коде без локов.

**Очереди обработки:** FIFO admission-queue корректна, deadlock не найден. Нет защиты от `max_concurrent_jobs` = 0 или отрицательного значения — очередь будет ждать вечно без явной ошибки конфигурации.

**Логирование/диагностика/observability:** `_redact_log_text` не редактирует произвольные пользовательские пути на нестандартных дисках (High, см. 2.3.13 — фильтр INFO-логов). `diagnostics_service.recent_errors()` отдаёт только короткое сообщение без traceback (полный traceback доступен отдельно через per-song лог). Correlation ID не связан со song_id-тегом фоновых job — по ID HTTP-запроса `/process` нельзя найти строки лога фоновой обработки.

**Error propagation:** `http_error()` теряет тип исключения, мапит все причины одного типа на один HTTP-статус — затрудняет диагностику при неинформативном `detail`.

**Секреты/privacy:** токен сравнивается через `hmac.compare_digest` — корректно. `remote_log_service.py` включена по умолчанию для собранных релизов без явного UI opt-out (Medium, см. качественная находка privacy).

**Зависимости:** версии зафиксированы разумными диапазонами. `yt-dlp` требует регулярных обновлений минимальной границы (YouTube часто ломает совместимость).

**Качество кода/naming/структура:** см. сводный раздел ниже.

**Тестирование:** 58 файлов, дисциплинированные, но систематически не тестируют конкурентный HTTP-доступ — ни одного теста с намеренной гонкой двух запросов к одной песне.

### 3.3 Нативная аудиоподсистема (WASAPI/ASIO)

**Latency:** приоритетная находка Critical (2.2.4). `wasapi_monitor_stream.py:98-110` — скрытая priming-буферизация ~2 периодов не отражена в latency-метриках, отдаваемых пользователю.

**DSP/audio quality:** расхождение алгоритмов эффектов ASIO vs Python (см. качество кода). Статический порог гейта (общий пункт с AI-разделом, применяется и здесь для recording-пути).

**Аудио (полный тракт):** ring-buffer (`monitor_buffer.h`) тщательно протестирован, однопоточный доступ подтверждён — гонок данных нет. Нет защиты от одновременного открытия микрофона standalone-монитором и записью на уровне backend (Medium) — оба могут захватить устройство параллельно в shared WASAPI-режиме.

**Стабильность:** физическое отключение устройства во время мониторинга корректно всплывает как исключение, но сообщение — сырой HRESULT-код без перевода в понятный текст. Нет watchdog для "тихо умершего" callback-потока во время записи.

**Отказоустойчивость:** падение/крах нативного WASAPI DLL или ASIO-бриджа после старта корректно обрабатывается (переход в error) — но этот путь не покрыт тестами.

**Восстановление состояния:** задокументированная в `MONITORING.md` ASIO4ALL-подсказка после "двух glitch-fallback" технически недостижима (см. качество кода — мёртвая функциональность).

**Lifecycle:** COM-объекты в `monitor.cpp` освобождаются в корректном (обратном) порядке — RAII отрабатывает даже при исключении в середине `open()`. Единственный поток команд (`monitor_control._run`) не имеет watchdog/таймаута на уровне самого цикла (текущий код аккуратен, но архитектурно хрупок к будущим изменениям).

**Race conditions:** `MonitorControl` реализует токен-based generation-counter, аналог RGB-контроллера — подтверждено тестами. Узкое окно гонки между конкурентным рестартом мониторинга и live-обновлением эффекта (Medium).

**Память/ресурсы:** ограниченные очереди/словари — утечек не найдено. GC-давление от частых мелких numpy-аллокаций в hot path (`microphone_quality.py`) — не утечка, но риск редких пауз GC в hard-realtime контексте на многочасовой сессии.

**Многопоточность/async:** блокировка (`threading.Lock`) внутри реального audio-callback потока в `monitor_worker.py` — несогласованность с lock-free паттерном, применённым в соседних файлах той же кодовой базы (Low-Medium).

**Файловая система:** не найдено логирования/дампа сырых аудиосэмплов на диск — все probe-инструменты явно документируют и соблюдают принцип "никогда не сохранять микрофонные сэмплы".

**Синхронизация времени:** экстраполяция между callback'ами ADC-часов корректно ограничена (`recording_service.py`) — защита от аномалий clock устройства продумана хорошо.

**Windows compatibility:** отсутствие MMCSS "Pro Audio" приоритизации потоков ASIO-бриджа (`bridge_main.cpp`), в отличие от остальных C++ аудио-компонентов этой же подсистемы (Medium).

**Error propagation:** сырые HRESULT-коды долетают до пользователя без перевода (см. выше). `error_text()` безопасно ограничивает длину буфера через `strncpy_s`.

**Качество кода:** см. сводный раздел ниже.

**Тестирование:** нет теста на исключение внутри `RecordingSession._callback` (Critical-баг из 2.2.5 не покрыт тестом). Нет теста на steady-state крах дочернего процесса мониторинга. Нет теста, подтверждающего, что событие `fallback` вообще когда-либо генерируется production-кодом.

### 3.4 Electron + RGB-подсветка

**Electron (main/renderer/preload):** разделение ответственности образцовое — preload тонкий, вся логика в main.cjs/модулях, `contextIsolation:true`/`sandbox:true`/`nodeIntegration:false`. Токен передаётся через sync-IPC с явным обоснованием, почему не через argv.

**Безопасность IPC:** `security.cjs` — самый строгий узел кодовой базы: единая `isTrustedIpcEvent` проверка для всех хендлеров, тест гарантирует 1:1 соответствие preload↔main каналов. Path traversal через фаззи-поиск папки песни невозможен (`realpathSync.native` + `isPathInside` до `shell.openPath`), но сама `isPathInside` не экспортируется из main.cjs и не покрыта unit-тестом (High test-gap, см. 2.3). Protocol handler `karaoke-media://` жёстко ограничен по hostname/pathname. Permission allowlist разрешает только аудио, camera/video запрещены даже при совместном запросе.

**Desktop UX:** force-kill backend через ~550мс во время активной AI-обработки без предупреждения пользователю (High). Нет persisted window state — всегда стартует fullscreen без учёта предыдущих предпочтений на мультимониторных системах (Medium). Fullscreen toggle и синхронизация с renderer реализованы корректно.

**Permissions:** allowlist оценивается как достаточно строгий, соответствует реальной потребности (запись микрофона).

**Lifecycle:** нет health-check для «зависшего, но живого» backend (High, см. 2.3.26). Fire-and-forget cleanup при выходе — `before-quit` не ждёт `lighting.close()`/`stopBackend()` через `event.preventDefault()` — риск оставить RGB-устройство в неверном состоянии при быстром выходе (Medium). Таймеры корректно чистятся в соответствующих stop/close обработчиках. Single-instance lock реализован верно.

**Race conditions:** generation counter в `rgb/controller.cjs` проверен внимательно, корректен и протестирован. `OpenRgb` класс не самозащищён от повторного параллельного `request()` (низкий риск — единственный вызывающий код уже сериализует вызовы).

**Память/ресурсы:** TCP-сокет в `openrgb.cjs` закрывается корректно. `MAX_PACKET`-ограничение защищает от неограниченного роста памяти. Нет `napi_add_env_cleanup_hook` для принудительного релиза LampArray-хендлов при аварийном завершении процесса.

**Стабильность/отказоустойчивость:** `protocol.cjs`-парсер устойчив к malformed-данным (все чтения через явную проверку границ). Отсутствующий/несобранный `KeyboardLighting.node` переживается gracefully. Частичная потеря enumerated-устройств при таймауте одного LampArray (Medium, см. 2.3.27 контекст).

**Windows compatibility:** Cyrillic-matching папок песен реализован корректно (учитывает Ё/ё). `isPathInside` корректно учитывает разные диски. Данные приложения намеренно хранятся рядом с exe, а не в `%LOCALAPPDATA%` — задокументированный design choice.

**Сборка:** жёсткая сетевая зависимость CMake configure (High, см. 2.3.29). Плохое сообщение об ошибке, если Visual Studio вообще не установлена (сырой ENOENT вместо понятного текста). Сборка нативного аддона блокирует релизный пайплайн при опциональной рантайм-роли (High, см. 2.3.28).

**Секреты:** токен генерируется заново при каждом запуске, передаётся только через sync-IPC, не протекает в логи. Токен в `contextBridge` неизбежно доступен JS в основном контексте страницы — конфиденциальность целиком зависит от CSP/отсутствия XSS (design note, стоит перепроверить CSP отдельно).

**Error propagation:** ошибки RGB-подсистемы нигде не логируются (High, см. 2.3.27). Статус из C++-аддона долетает до контроллера без потерь — теряется только детальный текст ошибки.

**Качество кода:** см. сводный раздел ниже.

**Тестирование:** сильное покрытие security.cjs/preload/protocol/RGB-генераций. Не покрыты: сам IPC-хендлер `shell:openSongFolder` целиком, `watchDuplicateBackend`/полный runtime `backend-process.cjs` (только статический regex-анализ исходника, не реальное поведение), нативный аддон lighting.cpp (только косвенный smoke-тест), build-lighting.mjs/CMakeLists.txt (нулевое покрытие).

### 3.5 Frontend React

**Архитектура:** в целом хорошая декомпозиция на хуки, но несколько крупных orchestrator-компонентов/хуков (см. качество кода). Много хуков системно используют `useLatestRef`/refs для устранения stale-closure — сильная практика.

**State management:** Blocker-уровня находка по откату аудионастроек (2.3.8). Тема применяется оптимистично без отката (Medium-High, см. 2.4). `useKaraokePreferences.js` — ошибка сохранения на backend полностью проглатывается (`.catch(()=>{})`) без обратной связи пользователю.

**React Hooks:** явных missing/лишних deps, условных хуков не найдено. `usePolling.js` — `refresh` зависит от потенциально нестабильного `query.refetch` — лишняя работа, не баг.

**React rendering:** `KaraokeLyrics`/`PianoRoll` используют кастомные memo-компараторы и прямую запись в DOM через refs внутри rAF — качественная оптимизация. Список песен в библиотеке без виртуализации (смягчено `content-visibility:auto`).

**UI responsiveness:** таймер 20 Гц с синхронным `getComputedStyle` в KeyboardLighting (Medium, см. 2.4). Основные тяжёлые вычисления (waveform, piano-roll) вынесены в rAF, не в тело рендера.

**UX/error handling:** см. state management выше. Двойной клик play/pause/stop защищён образцово через Symbol-токены операций.

**Accessibility:** слайдеры/метры снабжены aria-атрибутами. Глобальные хоткеи в редакторе перехватывают системный `Ctrl+A` без проверки фокуса в contenteditable-полях (Low).

**Internationalization:** полный паритет 710/710/710 ключей en/ru/uk, 0 расхождений плейсхолдеров. Хардкод "BPM" мимо i18n в двух местах (Low).

**Responsive UI/DPI:** подавляющее большинство стилей — относительные единицы/CSS custom properties. Декоративный canvas-визуализатор фона библиотеки содержит px-литералы (не критично).

**Визуальная консистентность:** нет централизованной z-index-шкалы (Medium, см. 2.4) — от 1 до 99999 разбросано по компонентам без системы.

**Синхронизация времени:** качественный дрейф-корректор с порогами none/soft/strong/hard, ресинхронизация по visibilitychange. NaN BPM edge case (High, см. 2.3.10). Edge cases "без нот"/"очень короткая песня" обработаны корректно.

**Latency:** несглаженные записи на backend при перетаскивании слайдеров/рукояток (High, см. 2.3.9) — главная находка раздела.

**Память/ресурсы:** все основные точки AudioContext/MediaStream (`keyboardLighting.js`, `useMelodyGuide.js`, `usePitchDetection.js`, `microphoneCapture.js`) имеют корректный cleanup — утечек не найдено. `radio.jsx` AudioContext не закрывается при размонтировании провайдера (низкий риск — провайдер уровня приложения, не размонтируется на практике).

**Race conditions:** `useKaraokeTransport` — образцовая защита от двойных кликов через operationRef/Symbol-токены. `useQueue()` сериализует сохранения по ключу поля, но не решает проблему заваленного бэкенда при быстром драге (получаем очередь однотипных запросов вместо гонки).

**Public interfaces:** `api/core.js` — единый 15-секундный таймаут для всех запросов включая потенциально долгие аплоады — стоит проверить отдельно. `isAmbiguousTransportError` системно используется для UX-различения сетевых сбоев — хорошая практика.

**Качество кода/дублирование/мёртвый код/сложность/naming/техдолг:** см. сводный раздел ниже.

**Тестирование:** сильное покрытие по основным хукам/компонентам. Пробелы: сценарий отсутствующего bpm не тестируется нигде, нет теста на откат `local`-состояния при ошибке сохранения, нет теста на частоту drag-запросов к API.

### 3.6 Online Room + Cloudflare

**Архитектура/Online Room:** комната материализуется как побочный эффект первого WebSocket-подключения к Durable Object; полный жизненный цикл (создание → апгрейд → проверки версии/вместимости/токена → приём сокета → снимок состояния → рассылка) реализован последовательно и продуманно.

**WebSocket-протокол:** нет монотонного `seq` на уровне DO — переупорядочивание разных команд не детектируется клиентом (Medium). Rate-limit по трём раздельным каналам (signal/ping/control) — сильная сторона, протестирована. Детект «полуоткрытого» сокета через clock-probe — качественная защита от tcp-зомби.

**Передача песен:** chunking с backpressure и кредитной схемой на приёме — корректно реализовано. Content-целостность через `sha256:`-проверку revision — хорошее сквозное подтверждение. Resume с прерванного байта не поддерживается (задокументированное ограничение, Medium, см. п.2.4 раздела Часть2 — при лимите файла 512МБ это заметная стоимость на нестабильной сети).

**Room State Machine:** kick участника отсутствует полностью (задокументированный продуктовый gap, не баг). Асимметрия host/guest при разрыве — host получает "reconnecting"-плейсхолдер, guest полностью пропадает из списка на весь grace-период (Medium). Host migration отсутствует (High, см. 2.3.24).

**Синхронизация плеера:** NTP-подобная синхронизация часов (ping/pong, минимальный RTT из 8 последних сэмплов) — качественное инженерное решение. Планирование старта воспроизведения заранее (executeAt) с компенсацией опоздания. Плавная дрейф-коррекция работает только локально (та же машина), между участниками — только дискретный heartbeat раз в 500мс (Medium) — при заметном джиттере это слышно как скачки, а не плавная подстройка.

**Сетевая деградация:** экспоненциальный backoff реконнекта, хорошо покрыт тестами. WebRTC-деградация — grace-таймер перед разрывом, явная диагностика TURN/relay в тексте ошибки. Нет приоритизации полосы между голосом и передачей файла в одном соединении (Medium, см. Часть 2.4).

**Offline-режим:** полная потеря сети обнаруживается двумя механизмами (heartbeat watchdog + connect timeout), UI корректно очищается. Нет предварительной проверки `navigator.onLine` до попытки подключения (Low, не решает проблему по существу, просто не оптимально по времени).

**Отказоустойчивость:** перезапуск/эвикция Durable Object обрабатывается корректно через `blockConcurrencyWhile` + WebSocket Hibernation API, протестировано. `this.rate`/`this.iceCredentials` не персистятся при восстановлении (минимальный риск). TURN недоступен по умолчанию без операционной видимости (High, см. 2.3.25). Непойманное исключение при переполнении R2-квоты в `handleLogUpload` (Low, не критичный путь).

**Восстановление состояния при reconnect:** host — полностью корректно и протестировано. Guest — сохраняется id через sessionToken, но видимость для остальных участников и восстановление позиции плеера имеют пробелы (High, см. 2.3.23 про start-karaoke).

**Race conditions:** TOCTOU-гонки на заполненность комнаты и "host уже подключён" (Medium, см. Часть 2.4). Конкурентные play/pause от разных участников — осознанное "последний принятый сервером побеждает", не баг.

**Данные:** SQLite-backed Durable Object класс включён, но реального SQL-кода нет — хранение через типизированный KV-интерфейс. Нет версионирования содержимого хранимых блобов сверх общего protocol version gate.

**Error propagation:** хорошо выстроенная цепочка сервер→UI с специфичными сообщениями. Единый слот `voiceError` перезаписывает конкурирующие сообщения об ошибках — предыдущая ошибка молча теряется из UI (Low-Medium).

**Секреты:** TURN-креды никогда не попадают клиенту, протестировано на "утечку". `hostToken` в query-параметре WebSocket URL (Medium, см. Часть 2.4). Гостевой доступ = знание room ID без пароля — осознанный продуктовый выбор, стоит явно задокументировать.

**Permissions:** матрица прав в основном enforce'ится на сервере, не только в UI — подделка `requesterId` явно отклоняется в тестах. `sync`-payload от хоста валидируется по форме гораздо слабее, чем гостевой путь (Low-Medium, осознанная граница доверия).

**Качество кода/naming/структура:** см. сводный раздел ниже.

**Тестирование:** backend Cloudflare — хорошее покрытие (worker.test.mjs, room-runtime.test.mjs, room-recovery.test.mjs). Фронтенд room-код — исключительно широкое покрытие. README документирует ручной 2-PC чек-лист перед релизом — часть пунктов там уже дублируется автотестами (избыточно), часть (реальный TURN/NAT, субъективное качество звука) объективно не автоматизируема сегодняшним стеком.

### 3.7 Сборка/релиз/зависимости/тестовая инфраструктура

**Сборка и установщик:** неподписанные сборки по умолчанию (Critical, 2.2.7). Жёсткий путь к VS2022 BuildTools без fallback через `vswhere.exe`. Два разных установочных механизма существуют параллельно (`npm run build:electron` с NSIS никогда не тестируется release-гейтом — реальный релиз идёт через Inno Setup) — путаница/техдолг.

**Installer upgrade:** реализовано хорошо — апгрейд определяется по наличию предыдущей установки, настройки читаются и применяются автоматически, AI-модели не перекачиваются повторно. Восстановление exe из локального архива при сбое апгрейда не имеет отката к предыдущей версии при повреждении самого архива (Medium).

**Uninstall:** статический `[UninstallDelete]`-список рассинхронизируется с реальным деревом Electron при минорных апдейтах (Medium, см. Часть 2.4). Пользовательские данные удаляются только с явного согласия — хорошо.

**Версии и миграции:** только аддитивные (add-column) миграции без версии схемы и down-migration (Medium, тот же класс проблемы, что в 3.2).

**Portable/reinstall:** данные хранятся внутри `{app}\data`, перенос папки установки переносит и данные — хороший, осознанный portable-дизайн. `GetDefaultDir` подставляет первый несистемный диск без проверки прав записи (Medium).

**Build reproducibility:** нет CI вообще (Critical, 2.2.6). Нет hash-пиннинга зависимостей (`requirements-lock.txt` сам это документирует). Release gate кэшируется по fingerprint инпутов и может пропустить полный перезапуск test suite без явного форса.

**Размер сборки:** есть рабочий инструмент (`generate-size-report.ps1`, bucket-классификация + поиск дублей по SHA256), но не является гейтом — раздувание не блокируется автоматически.

**Startup performance:** параллельный запуск фоновых джобов (npm ci, ASIO SDK restore, AI Core install) с поллингом и skip-check — грамотная оптимизация. `stop_dev_processes` безусловно убивает предыдущие dev-процессы без предупреждения об активной задаче (Low-Medium).

**Shutdown:** грамотно спроектированный graceful shutdown в `backend-process.cjs` (кооперативный POST + force-kill через таймаут). `smoke-packaged-backend.ps1` корректно останавливает процесс в finally.

**Зависимости:** ESLint 8 в состоянии EOL. Несовпадающие верхние границы numpy между двумя requirements-файлами. `miniflare` закреплён на alpha/nightly-версии как dev-зависимость (Medium).

**Dependency supply chain:** `pip_audit` не в обязательном гейте (High, 2.3.19). SBOM ограничен только name/version/license, не использует уже установленный `cyclonedx-python-lib`. ASIO SDK из неофициального форка (High, 2.3.20). MSST — production inference-движок из стороннего GitHub-репозитория без hash-проверки содержимого архива.

**Секреты:** подписывающий сертификат хранится как путь+пароль в env-переменных, не в коде — хорошая гигиена. Хардкод credentials не найден нигде в аудируемой зоне.

**Windows compatibility:** нигде не упомянуты Windows Defender exclusions при активном PyInstaller-фризинге нескольких exe (Medium) — риск ложных срабатываний AV.

**Тестовая архитектура:** 103 файла во фронтенде, e2e-директория содержит всего 2 файла на замоканном API; 57 файлов backend с плоской структурой. Дисбаланс сильно в сторону unit-тестов. Один flaky-паттерн найден (`waitForTimeout(6000)` вместо polling условия).

**Критические пользовательские сценарии:** нет сквозного e2e с реальным backend (High, 2.3.21).

**Масштабируемость:** нет load/scale-тестов нигде в репозитории (High, 2.3.22).

**Качество кода/naming/структура:** см. сводный раздел ниже. `backend/doc_dump_fixed.txt` — 100КБ постороннего документа в `backend/`.

**Технический долг:** TODO/FIXME не найдены нигде в `scripts/` — техдолг документируется развёрнутыми комментариями-обоснованиями вместо маркеров (хорошая практика, но такой долг легче не заметить, если не задокументирован явно).
