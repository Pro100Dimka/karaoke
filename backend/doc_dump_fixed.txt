# A&D Voice — ЕДИНОЕ ПОЛНОЕ ТЕХНИЧЕСКОЕ ЗАДАНИЕ
## Исправление, стабилизация, оптимизация, восстановление, совместимость и подготовка к production release

**Исходный проект:** `karaoke-main (5).zip`  
**Назначение документа:** это полностью автономное техническое задание. Для его выполнения не нужны никакие другие отчёты или аудиты: контекст, причины, требования, проверки и критерии готовности описаны непосредственно здесь.

---

# 0. Главная цель

Нужно не «подправить несколько ошибок», а привести проект в состояние, в котором:

- пользовательские данные не теряются и не портятся;
- повторная обработка песен работает предсказуемо;
- запись и анализ вокала дают корректный результат;
- Online Room переживает отключения, reconnect и transfer failures;
- приложение не деградирует по памяти после долгой работы;
- UI не фризит из-за React/WebGL/high-frequency state;
- AI pipeline не выполняет заведомо лишние гигабайты чтения и повторные decode;
- frontend/backend/Electron/Cloudflare используют согласованные контракты;
- изменения storage/model paths безопасны;
- ошибки не проглатываются и имеют диагностируемую причину;
- проект можно установить на чистую Windows и обновить поверх предыдущей версии;
- все критические пользовательские сценарии покрыты integration/E2E/regression проверками;
- после всех исправлений приложение проходит финальный release-readiness gate.

---

# 1. Обязательные правила выполнения

Эти правила действуют для **каждого этапа** ниже.

## 1.1. Не переписывать проект с нуля

Исправления делать постепенно. Сначала фиксировать существующее поведение, потом менять внутреннюю реализацию.

Запрещено одновременно:
- менять архитектуру;
- менять API;
- менять формат данных;
- менять UI;
- менять runtime-поведение;

если это не требуется конкретной задачей.

## 1.2. Сначала root cause, потом код

Для каждой проблемы исполнитель обязан сначала подтвердить:
1. где находится причина;
2. какой пользовательский сценарий её вызывает;
3. какие файлы участвуют;
4. какое состояние системы до ошибки;
5. какое состояние после ошибки;
6. почему существующие проверки не остановили проблему.

Только после этого менять код.

## 1.3. Не маскировать ошибки

Нельзя исправлять проблему только:
- дополнительным `try/except`;
- `.catch(() => {})`;
- увеличением timeout;
- повтором запроса;
- отключением проверки;
- скрытием кнопки;
- suppress warning;

если root cause остаётся.

## 1.4. Сохранять обратную совместимость

Особенно для:
- SQLite;
- старых песен;
- старых `lyricsSync.json`;
- `.karaoke.zip`;
- library folders;
- recordings;
- settings;
- ранее обработанных песен.

Если обратная совместимость невозможна — должна быть явная миграция.

## 1.5. Один source of truth

После рефакторинга не должно оставаться двух параллельных реализаций:
- нового и старого Models API;
- двух схем room messages;
- двух трактовок `source_path`;
- нескольких version constants;
- нескольких разных locking policies;
- нескольких независимых validation rules для `lyricsSync.json`.

## 1.6. После каждого этапа нужен отчёт

Для каждой задачи указывать:

- `DONE / PARTIAL / BLOCKED`;
- root cause;
- изменённые файлы;
- что именно исправлено;
- какие старые реализации удалены;
- какие проверки выполнены;
- результат проверок;
- остались ли известные риски.

Нельзя писать просто «исправлено».

# PHASE 0 — BASELINE И ИНВАРИАНТЫ

## 0.1. Зафиксировать основные пользовательские инварианты

До изменений явно закрепить:

### Song
- одна песня имеет стабильный `song.id`;
- artist + title не должны конфликтовать с другой песней только из-за одинакового title;
- DONE означает, что обязательные artifacts существуют и валидны;
- source и instrumental — разные понятия;
- reprocess не должен ломать уже существующую библиотеку.

### lyricsSync.json
- единственный authoritative документ текста/нот;
- `word.start < word.end`;
- ноты находятся внутри слова;
- ноты не перекрываются некорректно;
- note start/end finite;
- BPM/key валидны;
- документ можно безопасно редактировать, импортировать и мигрировать.

### Recording
- запись знает, с какого времени песни она началась;
- анализ использует абсолютное время песни;
- ошибка writer/device не должна оставлять runaway session.

### Room
- известно, кто host;
- известно, что происходит при выходе host;
- reconnect имеет определённую семантику;
- transfer имеет terminal state;
- song revision однозначен.

### Storage
- current и historical library roots имеют единый trust contract;
- изменение paths не происходит внутри другой файловой транзакции.

# PHASE 1 — КРИТИЧЕСКИЕ RUNTIME И DATA BUGS

Этот этап выполнять **до оптимизаций и крупных рефакторингов**.

## TASK 1.1 — Разделить original source и instrumental

**Приоритет:** CRITICAL  

### Проблема

После успешного pipeline:

```python
song.source_path = instrumental
```

То есть поле `source_path` сначала означает оригинальный upload, а после обработки — instrumental.

Если песня позже попадает в `ERROR`/`CANCELLED` и обычный `/process` запускается снова, pipeline может получить **instrumental вместо исходной песни**.

### Требуется

Убрать двойную семантику.

Предпочтительный контракт:

```text
original_source_path
instrumental_path
vocals_path
lyrics_document_path
```

Если оригинал намеренно удаляется после обработки:
- это должно быть отдельное явное состояние;
- полный reprocess без original должен быть запрещён;
- UI не должен предлагать действие, которое невозможно корректно выполнить.

### Проверить все места

- Song model;
- create/import;
- pipeline start;
- finalization;
- reprocess;
- delete;
- package export;
- package import;
- karaoke open;
- room transfer;
- diagnostics;
- tests;
- migrations.

### Acceptance

- ранее обработанная песня никогда не идёт в separation от instrumental как будто это original;
- `reprocess melody` работает без original;
- `full process` либо использует original, либо возвращает понятную ошибку;
- существующие библиотеки корректно мигрируют.

---

## TASK 1.2 — Исправить recording playback offset

**Приоритет:** CRITICAL  

### Проблема

`position_sec` существует только в live `RecordingSession`.

После сохранения Recording не знает, с какой позиции песни началась запись.

Analysis сейчас сравнивает:

```text
recording t=0
```

с:

```text
song t=0
```

вместо:

```text
song t=recording_offset
```

### Требуется

Добавить persistent:

```text
playback_offset_sec
```

в Recording model/schema/API.

Analysis:

```python
song_time = recording.playback_offset_sec + frame_time
```

Performance mix и analysis должны использовать **один и тот же offset contract**.

### Миграция

Для старых Recording:
- `playback_offset_sec = 0`;
- не ломать history.

### Acceptance

Запись, начатая на:
- 0 сек;
- 30 сек;
- 90 сек;
- 180 сек;

сравнивается именно с соответствующим участком reference.

## TASK 1.3 — Исправить duplicate identity песен

**Приоритет:** HIGH  

### Сейчас

```python
def _find_duplicate(db, artist, title):
    del artist
```

Сравнивается фактически только title.

### Требуется

Identity:

```text
normalized artist + normalized title
```

Продумать fallback, когда artist неизвестен.

### Нельзя

Нельзя просто разрешить любые дубли — иначе один и тот же файл будет импортироваться десятки раз.

### Acceptance

Разрешено:

```text
Artist A — Home
Artist B — Home
```

Но повторный импорт:

```text
Artist A — Home
```

распознаётся корректно.

---

## TASK 1.4 — Исправить historical library reprocess

**Приоритет:** HIGH  

### Проблема

Старые roots считаются trusted для чтения, но `_run_reprocessing()` разрешает только current `SONG_OUTPUT_DIR`.

### Требуется

Один общий path trust contract.

Либо:
- разрешить reprocess в historical root;

либо:
- атомарно мигрировать песню в current root перед reprocess.

### Acceptance

1. Песня создана в library A.
2. Пользователь меняет library на B.
3. Песня из A остаётся доступной.
4. Reprocess работает и не переводит её в ERROR.

---

## TASK 1.5 — Исправить package export/import round-trip

**Приоритет:** HIGH  

### Проблема

Legacy source включается в revision/export, но import его не публикует и canonical source становится instrumental.

Revision после import может отличаться.

### Требуется

Определить canonical portable package schema.

Рекомендуется:
- не дублировать source, если он равен instrumental;
- если source является самостоятельным обязательным artifact — реально сохранять его;
- revision должен вычисляться из canonical portable content;
- manifest должен явно описывать aliases.

### Acceptance

Обязательные cases:

```text
source == instrumental
source != instrumental
cover есть/нет
Unicode filenames
старый package
новый package
```

Для всех:

```text
export → import → compute revision
```

должен давать ожидаемый результат.

---

## TASK 1.6 — Исправить перенос notes при изменении lyrics

**Приоритет:** HIGH  

### Проблема

Notes сохраняются по индексу:

```python
previous[index]
```

Если слово вставили в начале — индексы всех последующих слов сдвинулись.

### Требуется

Не связывать identity слова с array position.

Варианты:
- stable `word.id`;
- `(start,end)` key;
- migration-aware matching.

### Acceptance

Если вставлено новое слово перед существующими, notes у неизменённых timed words не исчезают.

## TASK 3.1 — Исправить `PUT /lyrics` transaction

**Приоритет:** HIGH  

### Требуется

Использовать ту же discipline, что Editor:

```text

library transaction

atomic write
invalidate revision
touch Song
```

### Не допускать

```text

```

с потерей B.

---

## TASK 3.2 — Сделать storage path mutation транзакционной

**Приоритет:** HIGH  

### Сейчас

Global paths меняются без `library_write_lock()`.

### Требуется

Storage settings operation:
1. acquire global storage/library mutation lock;
2. убедиться, что нет несовместимых operations;
3. validate destination;
4. atomically switch configuration;
5. release;
6. notify dependent services.

Каждая операция должна использовать immutable path snapshot.

## TASK 3.3 — Запретить смену AI/cache folder во время model operation

**Приоритет:** HIGH  

### Требуется

Если model installer:

```text

verifying
repairing
```

storage selectors должны быть disabled/rejected.

Альтернатива — полноценная cancel/migration, но простое безопасное решение лучше.

Например:

# PHASE 5 — ONLINE ROOM

---

## TASK 5.1 — Host migration policy

**Приоритет:** CRITICAL/HIGH  

Сейчас host может уйти, а guests остаются.

Нужно выбрать **один** контракт:

### Вариант A — host migration
- deterministic next host;
- worker меняет role;
- frontend получает `host-changed`;
- permissions обновляются;
- transfer/UI ownership восстанавливается.

### Вариант B — host leaves → room closes
- guests получают explicit reason;
- transfers cancel;
- UI выходит из room;
- никаких hostless rooms.

Нельзя оставлять текущее неопределённое состояние.

---

## TASK 5.2 — Stable participant identity при reconnect


Нужен stable client/session id, чтобы reconnect не выглядел как полностью новый человек.

Сохранять:
- participant volume;
- effects;
- ownership;
- UI identity;
- transfer relation;

где это безопасно.

---

## TASK 5.3 — Resumable song transfer


Для больших package:

```text
transfer id
revision
total bytes
confirmed offset/chunk
```

После reconnect продолжать с подтверждённой позиции.

Если resume не реализуется — UI должен ясно сообщить restart.

---

## TASK 5.4 — Host disconnect mid-transfer

Любая transfer command должна немедленно перейти в terminal error/cancel при потере owner/host, а не ждать длинный timeout.

---

## TASK 5.5 — Shared Room Protocol


Frontend и Cloudflare должны использовать один:
- message schema;
- limits;
- enums;
- version;
- validation corpus.

---

## TASK 5.6 — Исправить byte limits

## TASK 5.7 — Permission model Room

Определить:

# PHASE 19 — ОТКАЗОУСТОЙЧИВОСТЬ ВСЕЙ СИСТЕМЫ

Цель этапа — доказать, что отказ любой внешней или внутренней подсистемы переводит операцию в понятное терминальное состояние, не портит пользовательские данные и не оставляет процессы/ресурсы работать бесконтрольно.

## TASK 19.1 — Падение backend процесса

### Проблема

Electron запускает backend как отдельный процесс. Если backend аварийно завершается во время обычной работы, frontend теряет API, а активные операции живут только частично в SQLite/filesystem.

Необходимо различать:

```text
backend ещё запускается
backend healthy
backend упал
backend был намеренно остановлен
backend завис
порт занят другим процессом
backend перезапускается
```

### Требуется

Создать явный `BackendSupervisor` с состояниями:

```text
STOPPED
STARTING
HEALTHY
DEGRADED
RESTARTING
FAILED
STOPPING
```

При unexpected exit:

1. записать exit code/signal;
2. зафиксировать app session/correlation id;
3. проверить наличие активных processing/recording операций;
4. не делать бесконечный restart loop;
5. выполнить bounded retry policy;
6. после исчерпания попыток показать пользователю конкретный error screen;
7. на следующем успешном старте выполнить recovery незавершённых операций.

### Обязательно проверить

- backend убит сразу после запуска;
- backend убит после healthy;
- backend убит в середине AI processing;
- backend завис и не отвечает health endpoint;
- порт занят;
- backend executable отсутствует;
- SQLite невозможно открыть;
- backend перезапустился, пока frontend открыт.

### Definition of Done

После любого из этих сценариев нет вечного loading, frontend знает состояние backend, а незавершённые Song/Recording состояния либо безопасно восстанавливаются, либо явно помечаются interrupted/error.

---

## TASK 19.2 — Падение AI/FFmpeg subprocess

### Проблема

AI pipeline зависит от внешних процессов/движков. Ошибка дочернего процесса не должна оставлять:

- `PROCESSING` навсегда;
- частичные outputs как финальные;
- orphan process;
- заблокированные файлы;
- ложный `DONE`.

### Требуется

Каждый child process должен иметь единый lifecycle:

```text
spawn
→ running
→ success
или
→ terminate requested
→ graceful terminate
→ timeout
→ kill process tree
→ await exit
→ cleanup
```

Finalization должна происходить только после проверки exit code и обязательных artifacts.

### Проверки

Искусственно:
- вернуть exit code 1;
- зависнуть навсегда;
- создать только один из output files;
- создать нулевой FLAC;
- завершиться во время cancellation;
- завершиться после того, как пользователь уже нажал Delete.

---

## TASK 19.3 — Disk full / read-only / исчезнувший диск

### Требуется

Все операции записи должны корректно обрабатывать:

```text
ENOSPC / disk full
permission denied
read-only filesystem
external drive removed
target folder deleted
rename failure
temporary folder unavailable
```

Особенно:

- recording;
- song processing;
- package import;
- package export;
- model download;
- settings save;
- database writes.

Перед длительными записями/скачиванием можно делать best-effort free-space preflight, но preflight не заменяет обработку реальной ошибки записи.

### Definition of Done

Ни одна ошибка диска не приводит к runaway RAM, ложному DONE или повреждению уже существующей рабочей версии песни.

---

## TASK 19.4 — CUDA/GPU failure

### Требуется

Обработать:

- CUDA недоступна при запуске;
- CUDA исчезла/driver error;
- `CUDA out of memory`;
- модель не помещается в VRAM;
- GPU занята другим процессом;
- unsupported capability.

Policy должна быть явной:

```text
GPU attempt
→ controlled cleanup
→ optional CPU fallback
или
→ понятная terminal error
```

Нельзя silently бесконечно повторять GPU operation.

# PHASE 20 — ВОССТАНОВЛЕНИЕ ПОСЛЕ ПЕРЕЗАПУСКА

## TASK 20.1 — Recovery незавершённой обработки песни

Diagnostics:

```text
liveness: process responds
readiness:
  DB readable/writable
  library writable
  ffmpeg available
  required models ready
  audio subsystem status
```

Не блокировать startup на optional capability, но показывать её состояние.

---

## TASK 35.2 — State transition logs

Для Song/Recording/Room/Transfer:

```text
oldState
newState
reason
operationId
duration
```

---

## TASK 35.3 — Ошибки нельзя превращать в silent null

Audit каждого:

```text
except: pass
except Exception: return None
.catch(() => {})
```

Для каждого решить:

1. expected and harmless cleanup;
2. optional degraded feature;
3. fatal operation error.

В первом случае допустим debug log, в остальных ошибка должна propagatе.

---

## TASK 35.4 — Log rotation

Ограничить:

```text
max file size
number of files
max total bytes
retention days
```

После установки обычный пользователь должен иметь write permissions на все mutable dirs.

Program Files/application binary directory не используется для user-generated data, если это требует admin.

---

## TASK 38.3 — Sleep/resume

Проверить sleep во время:

- idle;
- Karaoke playback;
- Online Room;
- Recording;
- model download.

После resume:

- audio devices revalidate;
- room reconnects;
- timers/clocks recalibrate;
- backend не считается mysteriously dead без retry.

## TASK 38.4 — Defender/antivirus delays

Но нельзя просто сделать огромный timeout: UI показывает startup progress и причину.

# PHASE 40 — BUILD REPRODUCIBILITY И SIZE

## TASK 40.1 — Release manifest

Каждая сборка генерирует:

```json
{
  "appVersion": "...",
  "sourceRevisionOrBuildId": "...",
  "node": "...",
  "npm": "...",
  "python": "...",
  "dependencies": {...},
  "models": [{"id":"...","sha256":"..."}],
  "ffmpeg": "...",
  "files": [{"path":"...","sha256":"..."}]
}
```

Это не зависит от наличия Git в пользовательском архиве: build id может задаваться build system/env.

---

## TASK 40.2 — Python lock

Release install использует frozen exact dependency set с hashes.

---

## TASK 40.3 — Build twice

Две чистые машины с одинаковыми inputs должны дать одинаковый logical manifest.

Byte-identical installer может различаться из-за timestamp/signing; это нужно учитывать отдельно.

---

## TASK 40.4 — Size report


# PHASE 46 — RELEASE BLOCKERS И PRODUCTION READINESS

Стабильный релиз **запрещён**, пока остаётся хотя бы один из следующих классов проблем:

## Блокирующие correctness

- full process может принять instrumental за original;
- recording analysis не учитывает playback offset;
- user-edited lyrics/notes могут быть потеряны из-за write/matching logic;
- portable package не round-trip;
- old library song ломается на reprocess.

## Блокирующие stability

- recording writer failure может бесконечно наращивать RAM;
- monitoring не восстанавливается после fatal recording stop;
- storage/model path race;
- Song может зависнуть в PROCESSING после crash.

## Блокирующие Online Room

- не определено поведение host disconnect;
- reconnect identity/state не согласованы;
- transfer failure/reconnect не имеет надёжного terminal/recovery поведения;
- player sync не выдерживает сетевую деградацию в заявленных пределах.

## Блокирующие compatibility

- нет доказанного upgrade старых DB/song formats;
- clean Windows install не проходит полный critical journey.

# PHASE 49 — ФИНАЛЬНЫЕ ИЗМЕРИМЫЕ КРИТЕРИИ

Проект можно объявить готовым только если одновременно выполнено следующее.

## Correctness

- critical user journeys зелёные;
- golden AI corpus не ухудшен сверх thresholds;
- recording from seek анализируется правильно;
- package round-trip preserves project;
- old supported project fixtures открываются.

## Stability

- disk/process/network/GPU fault matrix зелёная;
- нет вечных intermediate states;
- нет runaway queue;
- recovery после crash детерминирован.

## Resources

После soak:
- RSS имеет plateau;
- renderer heap имеет plateau;
- AudioContexts возвращаются к expected count;
- PeerConnections/DataChannels очищаются;
- VRAM не растёт от песни к песне без bounds;
- temp files не накапливаются.

## Performance

- Library 1k songs usable;
- Editor 10k notes usable в согласованном target;
- QFT не rebuild на обычном parent render;
- Karaoke не делает top-level React commit каждый animation frame;
- unchanged model readiness не перечитывает гигабайтный checkpoint;
- room revision sync не делает N requests на unrelated render.

## Room

- host disconnect работает согласно documented policy;
- reconnect работает предсказуемо;
- transfer failure имеет terminal reason;
- player drift находится в измеренном допустимом диапазоне.

## Desktop/Windows

- clean non-admin Windows install;
- Unicode/DPI/long paths;
- sleep/resume;
- second instance;
- close during processing/recording;
- upgrade N-1→N;
- uninstall policy проверен.

## Diagnostics

По одному пользовательскому diagnostic bundle можно восстановить:
- app/backend version;
- operation;
- state transitions;
- failure subsystem;
- error code;
- relevant timings;
- resource condition;
- без раскрытия secrets.

# ФИНАЛЬНАЯ ЦЕЛЕВАЯ МОДЕЛЬ

После выполнения задания система должна выглядеть концептуально так:

```text
Electron Desktop Shell
    │
    ├── BackendSupervisor
    ├── strict IPC/platform adapter
    └── React renderer
            │
            ├── feature-local UI state
            ├── server state client
            ├── high-frequency external stores
            └── Room client
                    │
                    ├── shared versioned protocol
                    ├── stable participant session
                    ├── transfer state machine
                    └── transport synchronization

FastAPI
    │
    ├── API adapters
    ├── Application services
    │      ├── ProcessingJobManager
    │      ├── Song service
    │      ├── Recording manager
    │      └── Package importer/exporter
    │
    ├── Domain
    │      ├── Song aggregate
    │      ├── lyricsSync schema/version
    │      ├── Recording timing
    │      └── state/error contracts
    │
    └── Infrastructure
           ├── SQLite
           ├── filesystem
           ├── FFmpeg/audio
           └── AI processor/model registry
```

Ключевой принцип:

```text
данные и state machines сначала
→ отказоустойчивость и recovery
→ audio/room/AI correctness
→ performance/resources
→ архитектурная декомпозиция
→ installer/production release
```

Нельзя менять эту последовательность ради косметического рефакторинга.
