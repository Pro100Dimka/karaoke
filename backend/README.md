# Karaoke AI — Backend

Локальный backend (FastAPI + SQLite) поверх существующего AI-пайплайна
(`AI/run_all.py`). Без UI — чистое API на `http://127.0.0.1:8000`,
документация автоматически на `/docs`.

## ⚠️ Перед тем как распаковывать поверх своего проекта

В этом архиве **нет** `AI/`, `full_songs/`, `Song/`, `venv/` — они у тебя уже
есть, я их не трогал и не дублирую. Также я **не видел** содержимого твоих
текущих `config.py` / `database.py` / `app/routers` / `app/services` (файлы

было — пришли их, я домержу, а не просто перезатру.

Структура архива:

```

```

```
├── venv/            ← твоё

├── database.py      ← новый

├── schemas.py        ← новый

```

## Запуск

```bash
pip install -r requirements.txt
python run.py
```

Откроется `http://127.0.0.1:8000/docs` — там же можно потыкать все ручки руками.

## Как это связано с AI/

`app/services/ai_bridge.py` один раз добавляет `AI/` в `sys.path` и напрямую
импортирует `run_all.run(...)`, `src.analyze.vocal.analyze_vocal(...)` и
т.д. — то есть backend не запускает `AI/run_all.py` как внешний процесс
через subprocess, а вызывает те же функции внутри своего процесса, в
фоновом потоке. Так проще следить за прогрессом: `run_all.py` и так печатает
шаги вида `6/13 ...` — `pipeline_service.py` перехватывает stdout,
парсит эти строки и пишет прогресс в БД, ничего не меняя в самом AI-коде.

## Что реализовано по каждому пункту ТЗ

**1. Управление песнями** — `POST/GET/PATCH/DELETE /songs`, статусы в
SQLite (`pending → queued → processing → done/error`), результаты AI
читаются из `Song/<slug>/*.json` по требованию (`GET /songs/{id}/result`),
не дублируются в БД.

**2. Запуск AI** — `POST /songs/{id}/process` дергает `run_all.run()` в
фоновом потоке (не блокирует API), сразу возвращает 202.

**3. Контроль обработки** — `GET /songs/{id}/status` отдаёт
`pending/queued/processing/done/error` + шаг вида `"6/13"` + процент.

**4. Чтение результатов AI** — `song_service`/`player_service` читают
`Song/<slug>/*.json` напрямую, backend ничего не парсит и не дублирует
сверх того, что уже посчитал AI.

**5. Управление файлами** — `cache_service.optimize_song_files()`
автоматически запускается после успешной обработки: `song/vocals/
instrumental.wav → mp3` (через `ffmpeg libmp3lame` — конвертер из `AI/`
пишет только PCM/wav, для mp3 у него отдельный вызов ffmpeg), удаляет
временные артефакты сепарации. Тот же метод доступен вручную —
`POST /cache/optimize/{song_id}`.

**6. API для React** — все группы ниже уже как реальные роутеры
(`app/routers/*.py`), не заглушки, кроме нескольких мест, явно
помеченных как упрощённые (см. ниже).

- **Песни** — `app/routers/songs.py`
- **Караоке-плеер** — `app/routers/player.py`. Сам звук проигрывает
  клиент; backend хранит серверное состояние (позиция/играет-стоит), чтобы
  разные части UI (текст/ноты/таймлайн) сверялись с одним источником
  правды, плюс отдаёт `sync`/`timeline` из уже посчитанных AI-данных.
- **Запись голоса** — `app/routers/recording.py` +
  `services/recording_service.py`. Реальный захват микрофона через
  `sounddevice`/`soundfile` (пишет `PCM_24`, см. ниже про стандарт
  форматов). Если `sounddevice`/PortAudio не установлены — ручки вернут
  понятную ошибку 503, а не уронят сервер.
- **Анализ голоса** — `app/routers/analysis.py` +
  `services/analysis_service.py`. Питчит запись пользователя через
  `AI/src/analyze/vocal.analyze_vocal` (та же функция, что и сам AI
  использует для эталона) и сравнивает с `reference.json` — точность
  (% попаданий в пределах полутона), среднее отклонение, разбивка по
  секциям из `structure.json`.
- **Кэш и производительность** — `app/routers/cache.py`.
- **Диагностика** — `app/routers/diagnostics.py`: проверка
  ffmpeg/demucs/whisper/torch/cuda, версии, последние ошибки обработки
  (читает `Song.error_message` у песен со статусом `error`).
- **Микрофон и звук** — `app/routers/audio.py`: список устройств
  (`sounddevice.query_devices()`), настройки (громкость/чувствительность/
  задержка/мониторинг) хранятся в SQLite, проверка уровня сигнала (RMS/
  клиппинг/тишина по короткой тестовой записи).

## Упрощения, о которых стоит знать

- `sensitivity` и "мониторинг голоса" в `AudioSettings` — это просто
  сохранённые значения, которые пока ни на что не влияют внутри backend'а
  (реальный live-мониторинг микрофона через колонки/наушники — это уже
  скорее задача клиента/аудио-движка, не REST API).
- Плеер не "проигрывает" звук сам — только синхронизирует состояние.
  Это осознанное решение: backend локальный и должен оставаться тонким,
  а сам звук логичнее гонять через клиентский аудио-движок (UI).
- SQLite: одна БД-файл в `data/app.db`, создаётся автоматически при
  первом запуске (`config.ensure_directories()` + `init_db()` при
  старте FastAPI).
